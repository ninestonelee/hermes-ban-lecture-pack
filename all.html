퇴근길 텔레그램 한 마디로 숏츠 초안 만들기

폰은 리모컨, 서버는 작업실. "숏츠 만들어"가 영상 파일로 돌아오는 구조

S 바로 활용6차시 PART 1 쇼츠 크론잡25분입문
원본 사례: @kookoo_Nick · 2026-10-21

한 줄 요약

퇴근길에 텔레그램으로 "숏츠 만들어"라고 보내면, 집 컴퓨터의 헤르메스가 대본, 음성, 자막을 넣은 영상 초안을 만들어 텔레그램으로 돌려준 국내 사례입니다.

원본 사례

2026년 10월 21일, 국내 사용자 쿠쿠(@kookoo_Nick)가 X에 올린 글입니다. 자기 집 윈도우 PC에 헤르메스 에이전트를 설치하고 텔레그램 봇과 연결해 쓰고 있다고 소개했습니다.

"폰으로 명령만 보내고, 진짜 작업은 컴퓨터에 시킴." (쿠쿠)

작성자가 밝힌 숏츠 제작 흐름은 이렇습니다.

  1. 텔레그램으로 주제를 보낸다
  2. 주제 분석
  3. AI가 대본 생성
  4. TTS(글을 목소리로 바꾸는 기술)로 음성 제작
  5. 자막 생성
  6. FFmpeg(영상 편집 프로그램)로 영상 편집
  7. 결과물을 텔레그램으로 전송

작성자는 "영상 소스 선정처럼 중간에 직접 확인하는 부분도 있다"고 밝혔습니다. 완전 자동은 아니고, 반복 편집 작업이 크게 줄었다는 이야기입니다. 숏츠 말고도 엑셀 10개 합치기, 사진 크기 일괄 변경, AI 뉴스 정리 파일 저장 같은 일을 같은 방식으로 시킨다고 했습니다.

같은 스레드 답글에는 윈도우 기준 설치 순서도 정리했습니다.

순서 작성자 안내 우리 수업에서는
1 PowerShell로 헤르메스 설치 라이트하우스 서버에 설치 완료
2 hermes setup, hermes model로 AI 연결 ChatGPT·Codex 구독 연결 완료
3 @BotFather에서 봇 만들고 토큰 받기 완료
4 hermes gateway setup으로 토큰과 내 숫자 ID 등록 완료
5 폰에서 명령 보내기 매일 하는 중

작성자의 결론 한 줄이 이 사례의 핵심입니다.

"중요한 건 AI가 갑자기 똑똑해지는 게 아니라, AI에게 실제로 일할 수 있는 도구를 쥐여준다는 거임." (쿠쿠)

참고: 작성자의 숏츠 스크립트 내용, 사용한 AI 모델, 제작 시간, 결과 영상은 공개되지 않았습니다.

왜 헤르메스반에 중요한가

  • 우리가 1차시부터 만든 구조와 똑같습니다. 다른 점은 작성자는 집 PC, 우리는 클라우드 서버라는 것 하나입니다. 작성자도 "클라우드 서버에 설치하면 집 PC 없이 운영 가능"하다고 썼습니다.
  • 집 PC 방식은 컴퓨터와 게이트웨이를 계속 켜 둬야 합니다. 서버 방식은 그 걱정이 없습니다. 우리가 왜 서버를 골랐는지 수강생이 스스로 납득하는 사례입니다.
  • 6차시 PART 1의 "이미지 합성형 쇼츠(카드뉴스 + 나레이션, 무료)"와 흐름이 같습니다. 이미 만든 카드뉴스 5장에 목소리와 자막만 붙이면 됩니다.
  • 5차시에서 배운 "미리보기 → 통과" 규칙을 영상에도 그대로 씁니다. 작성자도 중간 확인을 남겨 뒀습니다.

구조 한눈에 보기

  1. 1텔레그램 명령폰에서 "숏츠 만들어: 주제" 전송
  2. 2대본헤르메스가 30초 분량 대본과 카드 문구 작성
  3. 3음성Edge TTS로 한국어 나레이션 생성 (무료)
  4. 4자막과 편집FFmpeg가 카드 이미지 + 음성 + 자막을 세로 영상으로 합성
  5. 5미리보기텔레그램으로 영상 파일 전송, 내 답 기다림
  6. 6통과버퍼로 예약하거나 보관

폰은 "무엇을"만 말하고, "어떻게"는 서버가 합니다. 그래서 퇴근길 지하철에서도 영상 한 편을 맡길 수 있습니다.

핵심 개념

  • 게이트웨이: 텔레그램과 헤르메스를 잇는 통역사. 꺼져 있으면 봇이 조용해집니다.
  • TTS: 글을 목소리로 읽어 주는 성우. 헤르메스 기본값인 Edge TTS는 무료이고 키가 필요 없습니다.
  • FFmpeg: 명령어로 움직이는 영상 편집기. 사람이 마우스로 할 자르기, 붙이기, 자막 입히기를 글자 명령으로 합니다.
  • 허용 사용자 ID: 봇의 출입 명단. 내 숫자 ID만 적어 두면 다른 사람이 내 봇에 명령할 수 없습니다.
  • 스킬: 한 번 성공한 작업 순서를 저장한 레시피. 다음부터 "그 레시피대로"라고만 말하면 됩니다.

실습: 따라 하기

목표: 주제 한 줄을 보내면 30초 세로 영상 초안이 텔레그램으로 오게 만들기. 원본처럼 대본부터 편집까지 하되, 처음에는 카드 3장짜리 작은 버전으로 합니다.

1단계: 도구 점검 (3분)

봇이 영상 작업을 할 수 있는 상태인지 먼저 물어봅니다.

텔레그램 · 내 봇에게
영상 만들기 실습을 할 거야. 바꾸지 말고 점검만 해 줘.
1) 서버에 ffmpeg가 설치돼 있는지
2) 지금 TTS 설정이 무엇인지 (provider, 한국어 목소리 가능 여부)
3) 한글 폰트가 설치돼 있는지

봇이 설치 목록을 보여 주면 확인 후 "설치해"라고 답합니다. 위험한 명령이면 헤르메스가 승인 버튼을 띄웁니다.

설정이 끝나면 "안녕하세요, 헤르메스반입니다"를 음성으로 보내 줘.

3단계: 숏츠 초안 1편 만들기 (10분)

텔레그램 · 내 봇에게

2) 카드 3장을 세로(1080x1920) 이미지로 만든다 (디자인.md 스타일)
3) 대본을 Edge TTS 한국어 목소리로 읽어 음성 파일을 만든다
4) ffmpeg로 카드 이미지 + 음성 + 하단 자막을 합쳐 mp4로 만든다
5) 완성 영상을 텔레그램으로 보내고, 대본도 글로 같이 보내 줘

응용 아이디어

  • 소상공인: "오늘의 메뉴 숏츠"를 매장 사진 3장과 음성 설명으로. 아침 크론잡으로 매일 초안 받기.
  • 1인 크리에이터: 블로그 새 글이 올라오면 자동으로 숏츠 초안까지. 밤 11시 크론잡에 4단계를 붙이기.
  • 강사: 강의 핵심 요약 30초 영상. 수업 다음 날 수강생 단톡방 공지용.
  • 직장인: 주간 보고 내용을 1분 음성 브리핑으로. 영상 대신 음성 파일만 받아 출근길에 듣기.
  • 부동산·보험 상담: 자주 받는 질문 1개를 카드 3장 숏츠로. 상담 전 고객에게 보내는 안내 자료.

수강생 미션

기본 미션

"숏츠초안" 스킬을 저장하고, 폰에서 주제 한 줄을 보내 영상 초안 1편을 받기. 제출물: 텔레그램 대화 캡처(명령 1장 + 영상 미리보기 1장).

도전 미션

밤 11시 크론잡에 숏츠 초안 만들기를 추가하고, "통과"라고 답하면 버퍼로 유튜브 쇼츠에 예약되게 하기(6차시 PART 2와 연결). 제출물: 버퍼 캘린더에 쇼츠 예약이 보이는 캡처.

체크리스트

  • 봇이 ffmpeg, TTS, 한글 폰트 상태를 점검해 보고했다
  • 한국어 음성 메시지를 받았다
  • 카드 3장짜리 세로 영상 초안을 받았다
  • "수정: ..."으로 한 번 이상 고쳐 봤다
  • 과정을 스킬로 저장했다
  • 바로 게시하지 않고 미리보기 후 승인하는 규칙을 유지했다
  • 허용 사용자 ID에 내 숫자 ID만 있는지 확인했다

주의할 점과 한계

  • 봇이 털리면 서버도 털립니다. 원문 댓글에서도 같은 질문이 나왔습니다. 허용 사용자 ID에는 내 숫자 ID만 두고, 봇 토큰이 노출되면 @BotFather에서 /revoke로 즉시 폐기합니다.
  • 집 PC 방식의 한계: 원문처럼 집 PC에서 돌리면 PC와 게이트웨이가 꺼지면 아무 일도 못 합니다. 우리 서버 방식은 이 문제가 없지만, 서버 용량을 영상 파일이 빨리 채웁니다. 오래된 영상은 주기적으로 지우게 하세요.
  • 비용: 헤르메스와 Edge TTS는 무료지만, 대본을 쓰는 AI 모델 사용량은 구독 한도를 씁니다. 영상 생성형(힉스필드 등)은 별도 유료입니다.
  • 저작권: 남의 영상, 음악, 이미지를 소스로 쓰지 마세요. 내 블로그 글과 직접 만든 카드 이미지만 씁니다.
  • 미검증 부분: 원작성자의 숏츠 스크립트, 모델, 제작 시간, 결과물 품질은 공개되지 않았습니다. 이 교재의 실습은 원문 흐름을 우리 환경에 맞게 다시 설계한 것입니다.
  • @userinfobot: 원문은 숫자 ID 확인에 이 제3자 봇을 안내했습니다. 우리 수업에서는 이미 등록을 마쳤으니 다시 쓸 필요는 없습니다.

강사 노트

시간 내용
0~4분 원문 소개: "폰은 리모컨, PC는 작업실" 한 문장, 집 PC와 우리 서버 비교 표
4~7분 1~2단계: 도구 점검, 한국어 음성 테스트 (전원 동시)
7~17분 3단계: 숏츠 초안 1편 (대기 시간에 구조도 설명)
17~22분 4단계: 수정 1회 + 스킬 저장
22~25분 5단계 시연과 미션 안내, PART 2(버퍼 쇼츠 예약)로 연결

시연 팁:

  • 영상 생성은 수 분 걸릴 수 있습니다. 강사 봇으로 미리 1편 만들어 두고, 수강생 영상이 오는 동안 그 영상을 보여 주세요.
  • ffmpeg나 한글 폰트가 없어 실패하는 경우가 가장 많습니다. 1단계 점검을 꼭 먼저 하세요. 자막 한글이 네모로 깨지면 폰트 문제입니다.

원본 사례

2026년 11월 21일 밤, 국내 사용자 @koreabuldak이 자신의 글감 자동화 세팅을 공개했습니다. 집의 맥 스튜디오(애칭 "맥순이")를 24시간 켜 두고, 일을 셋으로 나눴습니다.

담당 하는 일 언제
감시기 1: 속보 네이버 속보 기사 100건을 훑고, 45분 안에 여러 매체가 같은 사건을 쓰기 시작하면 폰 알림 5분마다

감시기 3: 화제 논란 놓친 화제를 잡기 위해 새로 추가 수시
헤르메스 밤사이 모인 것을 "누구 얘기인가"로 나누고 글감 후보를 골라 메일 한 통 매일 08:00
클로드 알림을 붙여 넣으면 기사부터 다시 대조하고 형식 점검까지 마친 초안 작성 필요할 때

알림에는 꼬리표가 붙습니다. "AI화제, 논란, 생활행동, 민감"으로 나누고, 정치 공방이나 드라마 줄거리는 알림 없이 기록만 남깁니다. 첨부된 알림 화면에는 "[AI화제] 키워드, 구글트렌드 2,000+, 기사 6곳, 첫 기사 14:29"처럼 숫자 근거와 기사 3건 목록이 함께 나옵니다.

흥미로운 반전도 있습니다.

"그런데 오늘 제일 잘 터진 글은 감시기가 놓치고 내가 TV 보다 찾은 정재승 글이었음." (@koreabuldak)

그래서 지금은 조회수가 잘 나온 글을 보고 알림 기준을 스스로 고치게 만드는 중이라고 합니다.

같은 작성자가 답글에서 밝힌 운영 방식도 배울 점이 많습니다.

  • 점검도 단계를 나눔: 매주 스크립트가 환경 상태 수집 → 헤르메스(로컬 모델)가 1차 분석, 제안만 → 한 달에 한 번 클로드가 검증 → 본인이 최종 승인해야 수정. 검증 단계에는 파일 수정 권한을 아예 주지 않았다고 합니다.
  • 비용: 다른 서비스를 쓰고 싶지만 "비용 아끼려고 헤르메스를 쓴다"고 했습니다. 로컬 모델로 돌리려면 메모리 96GB 이상이 필요하다고 했습니다(작성자 주장).
  • 아직 실험 중: X 통계 CSV를 매일 분석해 글감을 찾게 했지만 "아직은 만족스럽지 않다"고 솔직하게 밝혔습니다.

참고: 수집 코드와 판정 로직은 공개되지 않았습니다.

왜 헤르메스반에 중요한가

  • 우리 파이프라인은 "블로그 글 → 밤 11시 크론잡 → 쓰레드·카드뉴스 → 승인 → 버퍼"였습니다. 이 사례는 그 앞단, 즉 "무엇을 쓸까"를 자동화합니다. PART 3 전체 파이프라인 지도에 한 칸을 더 붙일 수 있습니다.
  • 3차시에 건 크론잡은 "정해진 시각에 한 번" 도는 방식입니다. 이 사례는 "자주 지켜보다가 일이 생길 때만 말하는" 감시기 방식을 보여 줍니다. 헤르메스 공식 문서에도 바로 이 패턴이 있습니다.
  • "제안만 하고, 사람이 승인해야 수정"은 5차시 "통과·취소·수정" 규칙과 같은 철학입니다. 자동화가 늘수록 이 원칙이 더 중요해집니다.

구조 한눈에 보기

  1. 1감시기30분마다 내 분야 뉴스 확인, 새 소식 없으면 조용히 넘어감
  2. 2알림여러 매체가 같은 이야기를 쓰면 꼬리표 붙여 텔레그램 알림
  3. 3기록알림 안 한 것도 파일에 기록만 남김
  4. 4아침 정리08:00 헤르메스가 기록을 읽고 글감 후보 3개 선정
  5. 5미리보기텔레그램(또는 메일)으로 글감 브리핑, 내 선택 기다림
  6. 6초안고른 글감으로 블로그 초안, 이후 밤 11시 크론잡으로 연결

핵심은 역할 분리입니다. 감시기는 모델을 거의 쓰지 않고 지켜보기만 하고, 생각이 필요한 정리는 하루 한 번만 합니다. 그래서 구독 한도를 아낄 수 있습니다.

핵심 개념

  • 감시기(watchdog): 경비원. 이상이 없으면 말이 없고, 일이 생기면 그때만 보고합니다.
  • no-agent 크론: 모델 없이 스크립트만 정해진 시각에 돌리는 작업. 출력이 비어 있으면 아무 메시지도 안 옵니다. 토큰이 들지 않습니다.
  • 꼬리표 규칙: 우체국 분류함. 알림을 종류별로 나누고, 관심 없는 종류는 기록만 하게 합니다.
  • 작업 연결(context_from): 이어달리기 바통. 앞 크론잡의 결과를 다음 크론잡이 자동으로 이어받습니다.
  • 제안과 승인 분리: 결재 서류. 봇은 기안만 올리고, 도장은 사람이 찍습니다.

실습: 따라 하기

  • 투자 공부: 관심 종목 키워드에 공시·기사가 2곳 이상 나오면 알림. 매매 판단은 반드시 직접.

수강생 미션

기본 미션

감시기 1개(30분 간격)와 아침 8시 글감 브리핑 1개를 등록하고, 다음 날 아침 브리핑을 받기. 제출물: "등록된 크론잡 목록" 캡처 + 아침 글감 브리핑 캡처.

도전 미션

아침 브리핑에서 고른 글감으로 블로그 초안을 받고, 그 글이 밤 11시 크론잡을 거쳐 버퍼 예약까지 이어지게 하기(글감 → 블로그 → 쓰레드·인스타 전체 흐름). 제출물: 같은 주제가 글감 브리핑, 블로그 초안, 버퍼 캘린더에 이어진 캡처 3장.

체크리스트

  • 감시할 키워드 3개와 출처(RSS)를 정했다
  • 수집 출처의 이용약관을 확인했다
  • 감시기가 "알릴 것이 없으면 조용히" 동작한다
  • 같은 기사를 두 번 알리지 않는다
  • 꼬리표 규칙으로 알림과 기록만을 나눴다
  • 아침 8시 브리핑이 텔레그램으로 왔다
  • 점검 크론잡은 제안만 하고 직접 고치지 않는다

주의할 점과 한계

  • 수집 출처 규칙: 원본은 네이버 속보를 5분마다 훑습니다. 사이트마다 자동 수집 허용 범위가 다르므로, 공개 RSS나 공식 API처럼 허용된 경로를 쓰고 너무 잦은 요청은 피하세요. 우리 실습이 30분 간격인 이유입니다.
  • 알림 피로: 감시기를 늘리면 알림도 늘어납니다. 원작성자도 꼬리표와 "기록만" 규칙으로 줄였습니다. 하루 알림이 10개를 넘으면 기준을 높이세요.
  • 감시기가 다 잡지는 못합니다: 원작성자도 가장 잘 된 글감은 TV를 보다 직접 찾았습니다. 레이더는 보조 도구입니다.
  • 크론잡 안전장치: 헤르메스는 크론 실행 중 위험한 명령을 기본적으로 거부하고(cron_mode 기본값 deny), 크론잡이 또 다른 크론잡을 만들 수 없습니다. 이 기본값은 바꾸지 마세요.
  • 비용: 감시기를 no-agent로 만들면 모델 사용이 없습니다. 감시기를 모델로 돌리면 30분마다 구독 한도를 씁니다.
  • 미검증 부분: 원작성자의 판정 로직(45분 안 여러 매체), 실시간 검색어 출처, 메일 발송 방식, 로컬 모델 사양(메모리 96GB)은 작성자 주장이며 공개되지 않았습니다. 이 교재의 실습은 공식 문서의 크론 기능으로 다시 설계한 것입니다.

교재 03

텔레그램 속 작은 사무실, 칸반으로 AI 팀 나누기

비서 한 명에게 맡기면 기획, 리서치, 콘텐츠, 검수 담당이 나눠서 일하는 구조

S 바로 활용졸업 키트, 봇 여러 개로 역할 나누기 (3차시 크론잡 확장)30분중급
원본 사례: @moatrend · 2026-10-23

한 줄 요약

텔레그램에서 비서에게 "블로그 초안 잡아줘" 한 마디만 하면, 헤르메스 칸반(작업판)에 일이 등록되고 기획, 리서치, 콘텐츠, 검수 담당 봇이 차례로 나눠서 처리한다.

원본 사례

국내 사용자 Moa(@moatrend)는 2026년 10월 23일, 헤르메스 에이전트로 "텔레그램 안에 나만의 AI 팀"을 꾸렸다고 공유했다.

구조는 이렇다.

  • 사용자는 평소 쓰는 텔레그램에서 비서 봇에게 일을 맡긴다.
  • 맡긴 일은 칸반(작업판)에 카드로 등록된다.
  • 기획, 리서치, 콘텐츠, 검수 담당이 카드를 나눠 맡아 진행한다.
  • 사용자는 중간 질문에 답하고, 마지막 결과를 승인한다.

실제로 맡기는 요청의 예시도 함께 적었다.

"이 사진으로 블로그 소재를 만들어줘", "맛집 후기 자료 모아서 블로그 초안 잡아줘" 이런 요청을 맡기는 방식. 나는 텔레그램에서 요청하고, 중간 질문에 답하고, 결과를 승인한다. (@moatrend)

솔직한 한계도 남겼다. 클로드 코드를 써서 하루 종일 설정과 씨름했는데도 아직 도구 문제로 멈출 때가 있다고 한다. 그래도 "작은 사무실이 완성"됐다고 마무리했다.

댓글에서 "그록봇 대신 헤르메스를 쓰는 장점이 뭐냐"는 질문에는 이렇게 답했다.

제 서버에 깔아서 원하는 모델을 연결하고, 평소 쓰는 텔레그램에서 일을 맡길 수 있다는 게 좋더라고요. 옵시디언에 모아둔 제 자료랑 연결해서 작업하기도 좋고요. 대신 처음 설정하고 오류 잡는 건 제가 해야 합니다. (@moatrend)

원문에는 프로필 이름, 명령어, 모델 같은 세부 설정이 공개되지 않았다. 이 교재의 실습은 같은 구조를 헤르메스 공식 기능(프로필 + 칸반)으로 다시 설계한 것이다.

왜 헤르메스반에 중요한가

우리는 지금까지 봇 한 명에게 모든 일을 시켰다. 밤 11시 크론잡이 블로그 글로 쓰레드와 카드뉴스를 만들고, 텔레그램으로 미리보기를 보내고, "통과"하면 버퍼로 예약했다.

이 사례는 그 다음 단계다.

  • 같은 텔레그램, 같은 서버: 새 앱을 배울 필요 없이 지금 쓰는 봇이 "팀장" 역할을 맡는다.
  • 크론잡의 확장: 지금은 크론잡 하나가 생성부터 미리보기까지 혼자 한다. 역할을 나누면 리서치, 글쓰기, 검수를 각각 잘하는 담당자가 맡는다.
  • 승인 규칙 유지: Moa도 "결과를 승인한다"고 했다. 우리가 5차시에 배운 "미리보기 후 통과" 습관이 팀 구조에서도 그대로 핵심이다.
  • 검수 담당의 의미: 카드뉴스에 틀린 정보가 들어가는 사고를 사람 대신 검수 담당이 먼저 걸러 준다.

구조 한눈에 보기

  1. 1텔레그램 요청"맛집 후기 모아서 블로그 초안 잡아줘"
  2. 2비서(팀장) 봇요청을 칸반 카드로 등록
  3. 3칸반 분해프로필 설명을 읽고 담당자별 하위 작업으로 나눔
  4. 4리서치 담당자료 수집, 출처 정리
  5. 5콘텐츠 담당리서치 결과로 초안 작성
  6. 6검수 담당사실 확인, 맞춤법, 금지 표현 점검
  7. 7내 승인텔레그램으로 결과를 받고 통과 또는 수정

카드는 "부모 작업이 끝나야 자식 작업이 시작"되는 순서로 움직인다. 리서치가 끝나기 전에는 글쓰기가 시작되지 않는다. 앞 담당자가 남긴 요약은 다음 담당자에게 자동으로 넘어간다.

핵심 개념

  • 프로필(Profile): 직원 한 명의 책상. 각자 설정, 메모리, 스킬, 크론잡을 따로 가진다.
  • 프로필 설명(description): 직원 명찰. 칸반이 "이 일은 누구에게 줄까"를 정할 때 이 설명을 읽는다.
  • 칸반(Kanban): 사무실 화이트보드. 할 일 카드가 대기, 준비, 진행 중, 막힘, 완료 칸으로 이동한다.
  • 디스패처(Dispatcher): 화이트보드를 보고 1분마다 일을 나눠 주는 반장. 게이트웨이 안에서 돈다.
  • 분해(Decompose): 큰 일 하나를 담당자별 작은 일로 쪼개는 것. 기본값은 자동.

실습: 따라 하기

라이트하우스 서버의 헤르메스와 텔레그램 봇이 정상 작동하는 상태에서 시작한다. 봇이 대답을 안 하면 먼저 hermes model과 hermes gateway restart로 점검한다.

hermes profile create reviewer --description "초안의 사실, 출처, 맞춤법, 과장 표현을 점검하고 수정 요청을 남긴다"
hermes profile list
텔레그램 · 내 봇에게

텔레그램 · 내 봇에게
방금 만든 칸반 작업들의 상태를 칸별로 보여 줘.

결과가 오면 5차시 규칙대로 "통과", "취소", "수정: ..." 중 하나로 답한다. 이 단계까지는 어디에도 자동 발행하지 않는다.

응용 아이디어

  • 소상공인(음식점, 카페): 리서치(이번 주 지역 행사) → 콘텐츠(인스타 문구 3안) → 검수(가격, 영업시간 확인).
  • 1인 크리에이터: 리서치(유튜브 댓글 질문 모으기) → 콘텐츠(쇼츠 대본) → 검수(저작권, 과장 표현 점검).
  • 강사: 리서치(최신 사례 수집) → 콘텐츠(강의 슬라이드 개요) → 검수(출처 링크가 살아 있는지 확인).
  • 직장인: 리서치(경쟁사 뉴스) → 콘텐츠(주간 보고 초안) → 검수(숫자와 날짜 대조).
  • 부동산, 보험 설계사: 리서치(정책 변경 기사) → 콘텐츠(고객 안내 문자) → 검수(규정상 금지 표현 확인).

수강생 미션

기본 미션

프로필 3개(리서치, 콘텐츠, 검수)를 만들고, 칸반으로 블로그 초안 1건을 끝까지 돌려 본다.

제출물: hermes profile list 결과 캡처 1장, 텔레그램으로 받은 최종 미리보기 캡처 1장.

도전 미션

3차시에 만든 밤 11시 크론잡의 앞부분을 칸반으로 바꾼다. 크론잡이 직접 글을 쓰는 대신 "칸반에 작업을 만들고, 검수까지 끝난 결과만 미리보기로 보내기"로 고친다. 5차시 규칙(통과해야 버퍼 예약, 아침 8시까지 답 없으면 발행 안 함)은 그대로 유지한다.

제출물: 바뀐 크론잡 설명(봇에게 "등록된 크론잡 보여 줘"로 받은 내용) 캡처, 일주일 동안의 통과/수정 기록.

체크리스트

  • 프로필마다 구체적인 한 줄 역할 설명(description)을 넣었다
  • hermes profile list에 3개 프로필이 보인다
  • 텔레그램에서 칸반 도구를 켜고 새 대화(/new)를 시작했다
  • 작업이 리서치 → 콘텐츠 → 검수 순서로 진행되는 것을 확인했다
  • 막힌 작업이 생기면 이유를 봇에게 물어 해결했다
  • 최종 결과는 미리보기로만 받고 직접 승인했다
  • 비용이 걱정되면 담당자 수를 3명 이하로 유지했다

주의할 점과 한계

  • 원문 설정은 비공개: Moa는 프로필 이름, 명령어, 모델을 공개하지 않았다. 이 교재의 실습은 헤르메스 공식 문서의 칸반 기능으로 재구성한 것이다.
  • 설정이 어렵다: 원작성자도 하루 종일 씨름했고 "도구 문제로 멈출 때가 있다"고 했다. 처음엔 담당자 2~3명으로 작게 시작한다.
  • 비용: 담당자가 늘면 모델 호출도 늘어난다. 한 작업이 3명을 거치면 대략 3배 이상 쓴다고 생각하고, 구독 한도를 확인한다.
  • 봇 토큰은 한 프로필에만: 공식 문서에 따르면 텔레그램 봇 하나는 한 프로필에만 속한다. 담당자마다 별도 텔레그램 봇이 필요한 것은 아니며, 기존 봇이 팀장 역할을 하고 나머지는 칸반으로 일을 받는다.
  • 대시보드 주소: hermes dashboard는 서버 안에서 127.0.0.1:9119로 열린다. 라이트하우스 서버에서는 바로 브라우저로 볼 수 없으니, 수업에서는 텔레그램으로 상태를 묻는 방법을 쓴다.
  • 자동 분해 비용: 칸반의 대기(Triage) 칸에 넣은 작업은 기본 설정에서 자동으로 쪼개진다. 한 번에 많은 작업을 넣지 않는다.
  • 검수 담당도 AI다: 검수 담당이 통과시켜도 최종 확인은 사람이 한다.

툴보다 먼저, 에이전트 전용 계정과 놀이터 만들기

내 메인 메일과 PC를 지키는 가장 싼 보안

S 바로 활용6차시 PART 4 서버 지키기20분입문
원본 사례: @EKBaeAI · 2026-11-13

한 줄 요약

에이전트를 도입할 때 가장 먼저 할 일은 툴 고르기가 아니라, 에이전트만 쓰는 계정과 공간(놀이터)을 따로 만들어 "이 안에서만 일해"라고 경계를 정해 주는 것이다.

원본 사례

2026년 11월 13일, "AI Company Builder"를 소개하는 국내 사용자 배배(@EKBaeAI)가 X에 짧은 보안 조언을 올렸다. 핵심은 이 문장이다.

"AI 에이전트 도입할 때 제일 먼저 할 일은 툴 고르기가 아니라 '에이전트 전용 계정' 만들기예요." (@EKBaeAI)

작성자는 많은 사람이 자기가 쓰던 PC와 메인 메일에 바로 에이전트를 붙이는데, 그건 "진짜 비추"라고 말한다. 올해 초 OpenClaw와 헤르메스가 나왔을 때 사람들이 로컬 PC에 설치할 수 있었는데도 굳이 맥미니를 새로 샀던 이유가 "데이터 없는 빈 PC에서 시작하라"는 원칙 때문이었다는 것이다. (이 원칙의 출처는 작성자가 밝히지 않았다.)

작성자가 제안한 방법은 네 가지다.

  • 에이전트 전용 Gmail을 새로 만든다.
  • 그 계정에 딸린 드라이브, 캘린더 안에서만 일하게 한다.
  • 개인용 AI와 회사용 AI를 분리한다.
  • 회사 안에서도 대표, 인사처럼 민감한 정보를 보는 AI와 영업팀 AI를 나눈다.

작성자 본인의 구조도 소개했다. 그록봇에게 보내는 일은 거의 다 그록 전용 이메일로 보내고, 그록봇은 메일이 오면 지침을 받아 일한다. 전체를 지휘하는 메인 오케스트레이터는 헤르메스다.

답글에서는 "개인용과 회사용을 나누면 둘 다 알아야 하는 일정은 어떻게 하나"라는 질문이 나왔다. 작성자는 "일정은 공용 캘린더"로 해결한다고 답했다. 그리고 코인 서비스를 처음 쓸 때 원래 지갑 대신 따로 만든 지갑을 연결하는 것처럼, 새 에이전트 서비스도 그런 마음으로 대한다고 덧붙였다.

왜 헤르메스반에 중요한가

우리 수업에서 만든 봇은 이미 많은 출입증을 들고 있다.

  • 텔레그램 봇 토큰 (봇을 움직이는 열쇠)
  • ChatGPT/Codex 구독 로그인 (모델을 쓰는 열쇠)
  • 버퍼 API 키 (쓰레드, 인스타에 예약 게시하는 열쇠)

5차시에서 "API 키 = 출입증"이라고 배웠다. 이번 사례는 한 걸음 더 나간다. 출입증을 어디에 꽂을지, 즉 어떤 계정을 연결할지가 더 중요하다는 것이다. 봇이 내 메인 메일, 내 메인 드라이브에 연결되어 있으면 실수 한 번이 내 삶 전체로 번진다. 에이전트 전용 계정에 연결되어 있으면 사고가 나도 그 놀이터 안에서 끝난다.

다행히 우리 수업 구조는 이미 절반은 지키고 있다. 헤르메스는 내 노트북이 아니라 라이트하우스 클라우드 서버, 즉 "데이터 없는 빈 컴퓨터"에서 돌고 있다. 이제 남은 것은 계정을 정리하는 일이다.

구조 한눈에 보기

  1. 1나 (메인 계정)메인 메일, 개인 드라이브, 금융. 봇은 접근 금지
  2. 2공용 캘린더나와 봇이 함께 봐야 하는 일정만 공유
  3. 3에이전트 전용 Gmail봇이 메일 받고 보내는 유일한 주소
  4. 4전용 드라이브 폴더봇이 읽고 쓰는 파일은 여기만
  5. 5헤르메스 서버라이트하우스, 데이터 없는 빈 컴퓨터에서 시작
  6. 6업무용 프로필 분리개인용 봇과 업무용 봇은 키와 기억을 따로

위에서 아래로 갈수록 봇이 마음껏 움직여도 되는 공간이다. 맨 위 메인 계정에는 봇의 손이 닿지 않게 하고, 꼭 필요한 정보만 공용 캘린더나 전용 폴더로 내려보낸다.

핵심 개념

  • 에이전트 전용 계정: 봇 전용 업무용 휴대폰을 따로 만들어 주는 것. 회사 기밀이 담긴 내 휴대폰을 통째로 빌려주지 않는다.
  • 놀이터(작업 범위): 아이가 놀이터 울타리 안에서만 놀게 하는 것. 봇이 접근할 수 있는 폴더, 캘린더, 메일함을 정해 준다.
  • 최소 권한: 택배 기사에게 집 열쇠가 아니라 현관 무인택배함 비밀번호만 알려 주는 것. 일에 필요한 만큼만 권한을 준다.
  • 프로필: 같은 서버 안에 방을 여러 개 만드는 것. 헤르메스 공식 문서에 따르면 프로필마다 설정(config.yaml), 키(.env), 기억, 스킬, 크론잡이 따로 있다.
  • 허용 사용자 목록: 아파트 출입 명단. 텔레그램 봇에게 명령할 수 있는 사람을 정해 두지 않으면 모르는 사람도 말을 걸 수 있다.

실습: 따라 하기

모든 단계는 "보기만 하고 바꾸지 않기"부터 시작한다. 바꾸는 것은 내가 확인한 다음이다.

1단계: 내 봇이 지금 들고 있는 출입증 목록 만들기

텔레그램에서 내 봇에게 보낸다.

텔레그램 · 내 봇에게
지금 너에게 연결된 계정, API 키, MCP 서버, 로그인 목록을 표로 정리해 줘.
각 항목마다 "무엇을 할 수 있는지(읽기/쓰기/삭제/게시)"와 "어느 계정에 연결됐는지(개인/업무/전용)"를 적어 줘.
키 값은 절대 보여 주지 말고 이름만 적어. 아무것도 바꾸지 마.

결과를 보고 "개인" 표시가 붙은 항목에 동그라미를 친다. 그것이 정리 대상이다.

2단계: 에이전트 전용 Gmail 만들기 (내가 직접)

이 단계는 봇에게 시키지 않고 사람이 직접 한다.

  1. 새 구글 계정을 만든다. 예: 내이름.bot@gmail.com
  2. 비밀번호는 비밀번호 관리자에 저장하고, 2단계 인증을 켠다.
  3. 메인 계정에서 봇이 알아야 할 캘린더 하나만 새로 만들어 전용 계정에 "공유"한다. (작성자가 말한 "공용 캘린더")
  4. 메인 드라이브에 봇작업 폴더를 하나 만들어 그 폴더만 전용 계정과 공유한다.

3단계: 텔레그램 허용 사용자 확인

공식 문서에 따르면 허용 목록이 없으면 기본은 "모두 거부"다. 그래도 명시해 두는 것이 안전하다. 봇에게 확인만 시킨다.

텔레그램 · 내 봇에게
서버의 ~/.hermes/.env 에 TELEGRAM_ALLOWED_USERS 또는 GATEWAY_ALLOWED_USERS 설정이 있는지,
그리고 GATEWAY_ALLOW_ALL_USERS 가 켜져 있는지 확인해서 알려 줘.
값(숫자 아이디)은 가리고 "있음/없음"만 알려 줘. 아무것도 바꾸지 마.

GATEWAY_ALLOW_ALL_USERS=true가 있으면 강사에게 알리고 함께 고친다. 공식 문서는 이 설정을 "아끼는 기계에서는 절대 켜지 말라"고 안내한다. 참고로 헤르메스는 .env 파일을 파일 쓰기 도구로 고치지 못하게 막아 두었으므로, 수정은 서버 까만 창에서 사람이 직접 한다.

4단계: 승인 설정 확인

텔레그램 · 내 봇에게
~/.hermes/config.yaml 의 approvals 설정(mode, timeout, cron_mode, deny)을 그대로 보여 주고,
각각이 무슨 뜻인지 초등학생도 알게 한 줄씩 설명해 줘. 바꾸지는 마.

공식 기본값은 mode: smart(위험해 보이는 명령만 판단해서 물어봄), cron_mode: deny(크론잡이 위험 명령을 만나면 자동 차단), timeout: 300(5분 안에 답이 없으면 거부)이다. 우리 밤 11시 크론잡이 혼자서 위험한 일을 못 하는 이유가 바로 cron_mode: deny다.

5단계 (선택): 업무용 프로필 따로 만들기

개인 비서 봇과 업무용 봇을 나누고 싶은 분만 한다. 서버 까만 창에서 실행한다.

서버 터미널
hermes profile create work --no-credentials
work setup

공식 문서 기준으로 hermes profile create는 기본적으로 지금 프로필의 API 키와 모델을 가져온다. --no-credentials를 붙이면 키, 로그인, 모델을 하나도 복사하지 않은 빈 방이 생긴다. 업무용 키는 그 방에만 새로 넣는다. 프로필마다 텔레그램 봇 토큰도 따로 써야 한다(새 봇은 BotFather에서 하나 더 만든다).

응용 아이디어

  • 소상공인: 가게 예약 문의는 가게이름.bot@gmail.com으로만 받게 하고, 봇은 그 메일함에서 예약 초안만 만든다. 매출, 통장 관련 메일은 메인 계정에 그대로 둔다.
  • 1인 크리에이터: 버퍼에는 연습용 채널부터 연결해 2주간 돌려 본 뒤 본 채널을 연결한다. 작성자가 말한 "가짜 지갑부터 연결" 전략이다.
  • 강사: 수강생 명단과 연락처가 있는 시트는 봇에게 주지 않고, 이름을 지운 출석 통계 시트만 봇작업 폴더에 둔다.
  • 직장인: 회사 메일에는 절대 연결하지 않는다. 개인 학습, 블로그용 봇과 회사 일은 완전히 분리하고, 회사 도입은 회사 보안 담당과 상의한다.
  • 팀 단위: 작성자 조언처럼 대표/인사용 봇과 영업팀 봇을 다른 프로필로 나누고, 공유가 필요한 일정은 공용 캘린더로만 넘긴다.

수강생 미션

기본 미션

1단계 프롬프트로 "내 봇 출입증 표"를 받아, 개인 계정에 연결된 항목을 표시해 제출한다. 제출물: 표 캡처 1장 (키 값이 보이지 않는지 확인 후).

도전 미션

에이전트 전용 Gmail을 만들고, 공용 캘린더 1개와 봇작업 폴더 1개만 공유한 뒤, 봇에게 "공용 캘린더의 이번 주 일정 3개를 요약해 줘"를 시켜 성공 화면을 제출한다. 제출물: 공유 설정 화면 + 봇 답변 캡처.

체크리스트

  • 내 봇이 들고 있는 출입증(키, 로그인, MCP) 목록을 알고 있다
  • 메인 메일, 메인 드라이브에 봇이 직접 연결되어 있지 않다
  • 에이전트 전용 계정이 있고 2단계 인증이 켜져 있다
  • 봇과 공유하는 캘린더, 폴더는 꼭 필요한 것만이다
  • 텔레그램 허용 사용자 설정을 확인했고 ALLOW_ALL은 꺼져 있다
  • approvals 설정의 뜻을 설명할 수 있다
  • 키를 채팅에 보냈다면 연결 확인 후 그 메시지를 지웠다

주의할 점과 한계

  • 전용 계정을 만들어도 내가 메인 계정 자료를 봇에게 복사해 붙여 넣으면 소용이 없다. 경계는 계정보다 습관이다.
  • 공식 문서는 헤르메스의 안전장치(승인, 쓰기 차단, 비밀값 가리기)가 "정직하지만 실수하는 에이전트"를 막는 가드레일이지, 악의적인 프로그램을 가두는 감옥은 아니라고 설명한다. 완전 격리가 필요하면 도커 같은 격리된 실행 환경이 따로 필요하다.
  • /yolo 명령이나 승인 화면의 "always(항상 허용)"는 안전장치를 끄거나 영구 허용 목록에 넣는다. 수업 중에는 쓰지 않는다.
  • 프로필 분리는 서버 하나 안에서의 분리다. 서버 자체가 털리면 모든 프로필이 위험하다.
  • "올해 초 다들 맥미니를 샀다", "빈 PC에서 시작하라는 지침"은 작성자의 경험담이며 공식 문서 출처는 확인하지 못했다. 피클 보안이 "블랙박스"라는 평가도 작성자 의견이다.
  • 구글 계정을 여러 개 만드는 것은 구글 정책을 따른다. 계정 생성, 전화번호 인증 조건은 바뀔 수 있다.

한 줄 요약

봇에게 "점검만 하고, 내가 OK하기 전에는 아무것도 바꾸지 마"라고 시킨 뒤, 기억, 공간, 속도, 보안, 자동 실행 다섯 가지를 표로 보고받는 주간 건강검진 프롬프트입니다.

원본 사례

2026년 11월 24일, 헤르메스 팁을 꾸준히 올리는 @BkashJosi(Hermes Super-Intel)가 "헤르메스 5분 튠업"이라는 글을 올렸습니다. 하루 만에 조회수가 1만 3천을 넘었습니다.

글의 핵심은 헤르메스에 그대로 붙여 넣는 프롬프트 하나입니다. 첫 문장이 가장 중요합니다.

"내 헤르메스를 점검해 줘. 점검만 해. 내가 좋다고 하기 전까지 아무것도 바꾸지 마." (@BkashJosi, 번역)

그 다음 다섯 영역을 차례로 살피게 합니다.

영역 원문이 시킨 명령 봇에게 던지는 질문
기억(Memory) hermes memory status, hermes curator status 나에 대해 틀리거나 오래된 기억은?
공간(Space) hermes checkpoints status, hermes worktree audit, hermes sessions list 공간을 차지하는 것과 지워도 안전한 것은?
속도(Speed) hermes prompt-size 안 쓰는데 매 메시지를 무겁게 만드는 것은?
보안(Security) hermes security audit, hermes config get approvals 위험하거나 낡은 설정은?
자동 실행(Autopilot) hermes cron list, hermes fallback list 실패한 작업은? 예비 모델은 있나?

마지막에는 "영역, 발견한 것, 해결책 하나, 정확한 명령어" 네 칸짜리 표로 정리하고, 어떤 해결책을 적용할지 물어보게 합니다. 작성자는 "읽기만 한다. 네가 좋다고 하기 전에는 아무것도 바뀌지 않는다"며 매주 일요일에 실행하라고 권했습니다.

댓글에는 "잘 맞춰 놨다고 생각했는데, 이 프롬프트로 고칠 것을 여러 개 찾았다"는 사용자 후기도 달렸습니다.

공식 문서로 명령어를 하나씩 확인해 보니 9개는 실제로 있는 명령이었고, hermes worktree audit 하나는 문서에 없었습니다(비슷한 기능은 hermes worktree list). 그래서 우리 교재 버전에서는 이 명령을 빼고, 우리 환경에 더 맞는 읽기 전용 명령으로 바꿨습니다.

왜 헤르메스반에 중요한가

  • 5차시 승인 규칙의 연장입니다. 크론잡에 "통과라고 하기 전엔 발행하지 않는다"를 넣었듯, 서버 점검에도 "OK하기 전엔 바꾸지 않는다"를 넣습니다. 같은 습관입니다.
  • 봇이 조용해지는 원인을 미리 찾습니다. 5차시 오프닝에서 "0번, 봇이 대답을 안 한다"를 다뤘습니다. 예비 모델(fallback)이 없거나 크론잡이 실패하는 것을 미리 보면 그런 날이 줄어듭니다.
  • 밤 11시 크론잡을 지킵니다. 매일 도는 크론잡이 실패하고 있어도 텔레그램에서는 잘 안 보입니다. 튠업이 실패 기록을 찾아 줍니다.
  • 라이트하우스 서버는 작습니다. 세션과 기록이 쌓이면 디스크가 찹니다. 공간 점검이 필요합니다.
  • 까만 창을 몰라도 됩니다. 명령어는 봇이 서버에서 직접 실행하고, 우리는 텔레그램에서 결과 표만 봅니다.

구조 한눈에 보기

  1. 1일요일 아침텔레그램으로 튠업 프롬프트 전송
  2. 2읽기 전용 점검봇이 서버에서 점검 명령만 실행
  3. 3결과 표영역, 발견, 해결책, 명령어 4칸 표
  4. 4내 선택"2번만 적용해" 또는 "이번 주는 패스"
  5. 5적용과 확인고른 것만 적용 후 다시 점검

핵심은 3단계와 4단계 사이입니다. 봇이 표를 보여 주고 멈추는 지점이 있어야 합니다. 이 멈춤이 없으면 튠업이 아니라 "봇 마음대로 정리하기"가 됩니다.

핵심 개념

  • 읽기 전용(Check only): 건강검진처럼 보기만 하고 수술은 안 하는 것. 상태를 보는 명령만 씁니다.
  • 크론잡(cron): 정해진 시간에 자동으로 일하는 알람. 우리 밤 11시 작업이 이것입니다.
  • 예비 모델(fallback): 주 모델이 한도에 걸리거나 먹통일 때 대신 나서는 교체 선수.
  • 프롬프트 크기(prompt-size): 매 메시지마다 봇이 짊어지고 가는 기본 가방 무게. 안 쓰는 스킬이 많으면 가방이 무거워져 느리고 비싸집니다.
  • 승인 모드(approvals): 위험한 명령 앞에서 봇이 "해도 될까요?" 묻는 방식. smart, manual, off 세 가지가 있고 off는 위험합니다.

수강생 미션

기본 미션

  • 2단계 한국어 튠업 프롬프트를 내 봇에게 1회 실행합니다.
  • 제출물: 결과 표 캡처 1장 + "가장 먼저 고칠 것 하나와 이유" 한 줄.

도전 미션

  • 표에서 하나를 골라 4단계 방식(명령 미리보기, 통과, 재점검)으로 적용합니다.
  • 5단계 일요일 튠업 크론잡을 등록합니다.
  • 제출물: 적용 전후 표 캡처 + "등록된 크론잡 보여 줘" 결과 캡처.

체크리스트

  • 프롬프트 첫 줄에 "점검만, 적용이라고 하기 전엔 바꾸지 마"가 들어 있다
  • 봇이 표를 보여 준 뒤 멈추고 나에게 물었다
  • 밤 11시 크론잡의 최근 실패 여부를 확인했다
  • 예비 모델(fallback) 유무를 확인했다
  • approvals mode 가 off 가 아닌 것을 확인했다
  • 결과 화면에 API 키나 비밀번호가 보이지 않았다
  • 적용은 한 번에 하나씩, 미리보기 후 통과로 진행했다

주의할 점과 한계

  • "점검만"은 약속일 뿐 잠금이 아닙니다. 봇이 실수로 고칠 수도 있습니다. 승인 모드를 off 로 두지 말고, 이상한 명령이 보이면 바로 "멈춰"라고 보냅니다.
  • 원문 명령 중 하나는 공식 문서에 없습니다. hermes worktree audit 은 확인되지 않아 뺐습니다(워크트리는 개발자용 기능이라 우리 수업에는 필요 없습니다).
  • hermes memory status 는 외부 메모리 설정을 보여 줍니다. 봇이 나에 대해 무엇을 기억하는지는 명령보다 "나에 대해 뭘 기억하고 있어?"라고 직접 묻는 쪽이 정확합니다.
  • hermes security audit 은 외부 취약점 데이터베이스(OSV.dev)에 조회합니다. 서버 인터넷이 막혀 있으면 실패할 수 있습니다.
  • 비용: 점검 자체는 대부분 오프라인 명령이지만, 결과를 읽고 설명하는 데 모델 사용량이 듭니다. 매일이 아니라 주 1회면 충분합니다.
  • 버전 차이: 명령어는 2026년 11월 공식 문서 기준입니다. 서버 헤르메스가 오래됐다면 없는 명령이 있을 수 있습니다. 봇이 "그런 명령이 없다"고 하면 그 줄은 건너뛰게 합니다.
  • "5분"은 작성자 주장입니다. 스킬과 세션이 많으면 더 걸립니다.

한 줄 요약

매일 같은 모양으로 반복되고, 1분 안에 확인할 수 있는 결과가 나오는 일부터 크론잡으로 넘기면 됩니다. 순서는 읽기 → 분류 → 초안 → 외부 행동입니다.

원본 사례

싱가포르의 창업가 Dhawal Shah는 2026년 5월부터 Hermes Agent 위에서 "Nora"라는 비서를 운영합니다. 11월 24일 블로그에 Nora가 매주 실제로 하는 9가지 일과 결과를 표로 공개했습니다.

가장 먼저 추천하는 일은 아침 브리핑입니다. 작성자는 "읽기만 하니까 실수해도 잃을 게 없고, 일주일이면 도움이 되는지 안다"고 말합니다. 브리핑 형식은 날짜 → 오늘 일정 → 메일 요약 → 오늘 마감 후속조치 → 위험, 다섯 칸입니다.

실패한 일도 솔직하게 적었습니다. "남는 시간에 목표 작업을 넣어 달라"고 캘린더 권한을 줬더니, 한 달 동안 만든 24개 블록 중 20개가 기존 미팅 복사였고 목표 작업은 2개뿐이었습니다. 작성자의 결론은 이렇습니다.

"에이전트에게 필요한 것은 접근 권한이 아니라 정해진 결과물이다." (Dhawal Shah)

왜 헤르메스반에 중요한가

우리는 3~5차시에 밤 11시 크론잡 하나(블로그 → 쓰레드·카드뉴스)를 만들고, 미리보기 → 통과 → 버퍼 예약 흐름을 붙였습니다. 졸업 후 가장 흔한 질문은 "그다음엔 뭘 시키죠?"입니다. 이 사례는 그 답을 메뉴판으로 보여 줍니다.

  • 9가지 중 7가지가 텔레그램으로 결과를 받는 크론잡입니다. 우리 봇 구조와 똑같습니다.
  • 작성자의 안전 원칙(읽기부터, 멈춤 규칙, 보내기 전 승인)은 우리가 배운 통과/취소/수정 규칙과 같은 생각입니다.
  • 답장 초안 품질이 "더 좋은 모델"이 아니라 "더 좋은 지시서"로 좋아졌다는 점은 디자인.md, 규칙 1~6번처럼 지시를 구체적으로 쓰는 우리 수업 방식과 맞닿아 있습니다.

핵심 개념

  • 크론잡: 정해진 시각에 울리는 알람. 알람이 울리면 봇이 정해진 일을 합니다.
  • 홈 채널(/sethome): 크론잡 결과를 배달받는 우편함. 이 명령을 보낸 텔레그램 채팅으로 결과가 옵니다.
  • 정해진 결과물: "알아서 잘"이 아니라 "이 다섯 칸을 채워라". 칸이 있어야 1분 안에 검토할 수 있습니다.
  • 멈춤 규칙: 내가 확인하지 않으면 다음 회차를 쉬는 규칙. 안 읽은 결과가 쌓이지 않게 합니다.

주의할 점과 한계

  • 수치는 작성자 주장입니다. "첫 20분 대체", "30% → 7%" 등은 검증하지 않았습니다. 같은 작성자의 다른 노트에는 아침 브리핑이 "5~8분 절약"이라고 적혀 있어 숫자가 다릅니다.
  • 환경 차이: Nora는 구글 캘린더, Gmail(AgentMail), WhatsApp을 연결했습니다. 우리 수업에서는 이 연결을 다루지 않았으므로 레시피를 텔레그램, 메모, 뉴스 검색 위주로 줄였습니다. 메일·캘린더 연결은 별도 인증과 보안 검토가 필요합니다.
  • 크론잡은 위험 명령을 스스로 막습니다. 공식 문서상 크론 실행 중 위험한 명령이 나오면 기본값(cron_mode: deny)으로 사람에게 묻지 않고 차단합니다. 그래서 "통과" 같은 확인은 프롬프트 규칙으로 직접 넣어야 합니다.
  • 구독 사용량: 크론잡이 늘수록 ChatGPT·Codex 구독 사용량도 늘어납니다. 하나 추가할 때마다 일주일 지켜보세요.
  • 개인정보: 연락처, 건강 정보는 민감합니다. 이름 대신 별칭을 쓰고, 의료 판단은 하지 않도록 명시하세요.
  • 열린 지시는 실패합니다. "내 일주일을 계획해 줘"처럼 결과물이 정해지지 않은 일은 원본에서도 실패했습니다.

휴대폰이 리모컨, 위험한 일은 승인받고 하기

음성 메모, 승인 버튼, 백그라운드 작업, 홈 채널로 서버 봇을 밖에서 조종합니다

S 바로 활용4~5차시 승인 → 버퍼 예약 (통과·취소·수정 규칙)25분입문
원본 사례: @BkashJosi · 2026-11-01

한 줄 요약

서버는 집(클라우드)에 두고, 휴대폰으로는 지시하고 승인만 합니다. 헤르메스에는 위험한 명령 전에 사람에게 묻는 승인 기능이 기본으로 켜져 있습니다.

원본 사례

2026년 11월 1일, 헤르메스 팁을 꾸준히 올리는 @BkashJosi가 "휴대폰에서 헤르메스를 쓰는 5가지 방법"을 정리했습니다.

"노트북은 집에 있고, 헤르메스는 계속 일하고, 휴대폰이 그것을 조종한다." (@BkashJosi)

  1. 손이 바쁠 때, 음성 메모: 텔레그램 음성 메모가 글로 바뀌어 일반 메시지처럼 실행됩니다. 로컬 음성 인식은 키가 필요 없습니다.
  2. 명령이 미심쩍을 때, 휴대폰으로 승인: 텔레그램에 허용·거부 버튼이 오고, 아무 연결된 채팅에서 /approve 또는 /deny로 답할 수도 있습니다. 승인 기능은 기본으로 켜져 있습니다.
  3. 긴 작업일 때, /bg: /bg 작업내용을 보내고 휴대폰을 주머니에 넣으면 결과가 채팅으로 돌아옵니다.
  4. 채팅 앱이 없을 때, ntfy: 무료 ntfy 앱으로 답을 푸시 알림으로 받습니다.
  5. 크론잡 결과를 휴대폰으로, /sethome: 결과를 받을 채팅에서 /sethome을 보냅니다.

덧붙여, 텔레그램에서는 기본 설정상 최종 답과 승인 요청만 알림이 울리고 진행 중 메시지는 조용히 옵니다. 같은 날 공식 모바일 앱이 아이폰·안드로이드 오픈 베타로 나왔다고 알렸습니다.

왜 헤르메스반에 중요한가

5차시에 우리는 밤 11시 크론잡에 "텔레그램 미리보기 → 통과면 버퍼 예약, 취소면 발행 안 함, 수정이면 고쳐서 다시, 아침 8시까지 답 없으면 발행 안 함" 규칙을 붙였습니다. 이 사례는 그 생각이 헤르메스 안에 공식 기능으로도 들어 있다는 것을 보여 줍니다.

  • 우리가 만든 통과 규칙은 콘텐츠 승인입니다. 프롬프트로 직접 정한 규칙입니다.
  • 헤르메스 기본 승인은 명령 승인입니다. 파일 삭제처럼 위험한 서버 명령 앞에서 자동으로 멈춥니다.
  • 둘 다 "답이 없으면 하지 않는다"가 기본입니다. 우리 5번 규칙(8시까지 답 없으면 발행 안 함)과 공식 승인 타임아웃(기본 300초, 응답 없으면 거부)이 같은 원리입니다.
  • /sethome은 3차시에 크론 결과를 받을 때 이미 쓴 바로 그 기능입니다.

구조 한눈에 보기

  1. 1휴대폰글이나 음성 메모로 지시
  2. 2텔레그램 봇서버의 헤르메스에 전달
  3. 3헤르메스 판단안전하면 진행, 위험하면 멈춤
  4. 4승인 요청휴대폰에 알림과 버튼 도착
  5. 5사람의 답승인하면 실행, 거부나 무응답이면 중단
  6. 6결과같은 채팅 또는 홈 채널로 배달

핵심 개념

  • 명령 승인(Exec Approval): 공사장의 안전 관리자. 위험한 작업 앞에서 "진행할까요?"라고 꼭 묻습니다.
  • 승인 모드 smart(기본): 똑똑한 경비원. 안전한 건 통과, 확실히 위험한 건 차단, 애매하면 사람에게 물어봅니다.
  • 타임아웃: 대답 없으면 문을 닫는 자동문. 기본 300초 동안 답이 없으면 실행하지 않습니다.
  • /bg 백그라운드 작업: 심부름꾼을 따로 보내기. 지금 대화와 별개로 일하고 끝나면 보고합니다. 단, 지금 대화 내용은 모릅니다.
  • 홈 채널(/sethome): 크론잡 결과를 받는 우편함.

4단계: 승인 설정 점검

공식 기본값은 mode: smart, timeout: 300초, cron_mode: deny입니다. off나 yolo로 돼 있다면 강사와 상의하세요.

텔레그램 · 내 봇에게

다른 질문을 하면서 기다리다가, "Background task complete" 메시지로 결과가 오는지 확인합니다.

응용 아이디어

  • 소상공인: 매장에서 손이 바쁠 때 음성 메모로 "오늘 품절 메뉴 공지 초안 써 줘", 미리보기 후 통과.
  • 1인 크리에이터: 촬영 이동 중 /bg 이번 주 쇼츠 아이디어 10개 조사해서 표로.
  • 강사: 수업 직전 음성으로 "오늘 과제 제출 안 한 사람 명단 정리"(파일 정리만, 문자 발송 금지).
  • 직장인: 회의 중 /bg 어제 메모를 주간 보고 초안으로, 회의 끝나면 확인.
  • 가족 단체방: 봇을 단체방에 넣을 때는 승인할 수 있는 사람을 나로 제한(approvals.approvers)하는 설정을 강사와 함께 검토.

  • 음성 메모가 글로 바뀌어 실행되는 것을 확인했다

  • 크론잡의 통과 규칙(콘텐츠 승인)과 명령 승인의 차이를 설명할 수 있다

주의할 점과 한계

  • 크론잡은 명령 승인을 물어보지 않습니다. 공식 문서상 크론 실행 중 위험 명령은 기본값(cron_mode: deny)으로 그냥 차단됩니다. 밤사이 사람에게 묻는 구조가 아니므로, 콘텐츠 발행 같은 확인은 5차시처럼 프롬프트 규칙으로 넣어야 합니다.
  • YOLO와 off는 쓰지 마세요. 승인 모드를 off로 하거나 /yolo를 켜면 모든 안전 질문이 사라집니다. 공식 문서도 신뢰된 환경에서만 쓰라고 경고합니다.
  • 승인 전 명령을 끝까지 읽으세요. 공식 문서상 명령이 너무 길어 다 못 보여 주면 거부만 할 수 있게 됩니다. 이해 못 하는 명령은 거부가 정답입니다.
  • /bg는 지금 대화를 모릅니다. 필요한 정보는 /bg 문장 안에 모두 적어야 합니다.
  • 버튼 문구는 다를 수 있습니다. 원문의 "Allow Once / Deny" 버튼 이름은 공식 문서에서 정확히 확인하지 못했습니다. 문서에는 yes, approve, ok 등으로 승인하고 no, deny, cancel 등으로 거부한다고 적혀 있습니다.
  • 모바일 앱 상태: 원문은 11/1에 "오픈 베타"라고 했지만, 11/25 현재 공식 모바일 페이지는 베타 대기자 등록(waitlist) 화면입니다. 설치 가능 여부는 직접 확인하세요. 수업에서는 텔레그램만으로 충분합니다.
  • ntfy는 공식 지원 목록에 있으나 이번 교재에서 설정은 다루지 않았습니다.

교재 08

undo-effects, 봇이 지운 파일을 한 줄로 되살리는 안전장치

지우기 직전에 사본을 떠 두는 커뮤니티 플러그인으로 롤백 연습하기

S 바로 활용6차시 PART 4 서버 지키기 (롤백 시연)25분중급
원본 사례: @witcheer · 2026-11-07

한 줄 요약

봇이 파일을 지우거나 덮어쓰기 직전에 사본을 저장해 두고, /undo-effects restore 한 줄로 되돌리는 헤르메스 플러그인입니다.

원본 사례

헤르메스 커뮤니티 소식을 정리해 올리는 @witcheer가 2026년 11월 7일(미국 시각) 30초짜리 시연 영상과 함께 이 플러그인을 소개했습니다.

"헤르메스 에이전트가 파일을 지우거나 덮어썼다면, 명령 하나로 되돌릴 수 있다." (@witcheer, 번역)

만든 사람은 GitHub 사용자 Moodtuner997이고, MIT 라이선스 오픈소스입니다. 11월 4일에 저장소가 만들어졌고, 공식 헤르메스 플러그인 카탈로그에 커뮤니티 등급(community)으로 등록됐습니다. 버전은 0.1.2이고 헤르메스 0.22.7 이상이 필요합니다.

작동 방식은 단순합니다.

  1. 봇이 rm(삭제), mv(이동), sed -i(파일 안 글자 바꾸기), >(덮어쓰기) 같은 명령이나 파일 쓰기 도구를 실행하려고 하면,
  2. 실행 직전에 영향을 받을 파일을 몰래 복사해 둡니다.
  3. 명령은 원래대로 실행됩니다. 막거나 바꾸지 않습니다.
  4. 나중에 /undo-effects list 로 무슨 일이 있었는지 보고, /undo-effects restore 1 로 되돌립니다.

저장소 설명서에 나오는 예시 화면을 번역하면 이렇습니다.

text
> /undo-effects list
최근 효과 3개, 최신 순
  1  14:07:12  terminal    rm -rf build/ dist/      파일 2개, 1.2MB 저장
  2  14:05:40  write_file  src/config.py            파일 1개, 2.1KB 저장
  3  14:02:03  terminal    git clean -fd            지원 안 됨(not covered)

> /undo-effects restore 1
경로 2개 복원 완료. 교체된 내용도 보관했으니 다시 되돌릴 수 있음.

설명서가 강조하는 안전 규칙이 세 가지 있습니다.

  • 봇이 바꾼 뒤에 내가 직접 고친 파일은 덮어쓰지 않습니다. (강제로 하려면 --force)
  • 복원하면서 바뀌는 내용도 사본을 남겨서 복원 자체도 되돌릴 수 있습니다.
  • 분석하지 못한 명령은 조용히 넘어가지 않고 "not covered(지원 안 됨)"라고 솔직하게 표시합니다.

왜 헤르메스반에 중요한가

  • 6차시 PART 4 롤백 시연과 짝입니다. 깃허브 백업은 "프로젝트 전체를 예전 상태로", undo-effects 는 "방금 봇이 지운 파일 하나를 되살리기"입니다. 두 가지를 같이 알면 겁이 줄어듭니다.
  • 우리 봇은 서버에서 혼자 일합니다. 밤 11시 크론잡이 블로그 기록 파일이나 디자인.md 를 잘못 덮어써도 우리는 자는 중입니다.
  • 5차시 6번 규칙(이미 쓴 글은 다시 쓰지 않는다)은 기록 파일에 의존합니다. 그 기록 파일이 지워지면 같은 글이 또 올라갈 수 있습니다. 되살릴 방법이 있어야 합니다.
  • 설치가 한 줄입니다. 텔레그램으로 봇에게 시키면 됩니다. 4차시에 버퍼 MCP 를 봇에게 설치시킨 것과 같은 방식입니다.

구조 한눈에 보기

  1. 1봇의 작업크론잡이나 내 지시로 파일을 지우거나 덮어씀
  2. 2직전 사본undo-effects 가 대상 파일을 먼저 복사
  3. 3그대로 실행명령은 막지 않고 원래대로 실행
  4. 4사고 발견"어? 기록 파일이 사라졌네"
  5. 5목록 확인/undo-effects list 로 언제 무엇이 바뀌었는지 보기
  6. 6복원/undo-effects restore 번호 로 되살리기

헤르메스에는 비슷한 내장 기능인 체크포인트와 /rollback 도 있습니다. 다만 공식 문서에 따르면 체크포인트는 기본으로 꺼져 있어서 따로 켜야 합니다. undo-effects 는 플러그인을 켜기만 하면 git 저장소가 아닌 일반 폴더에서도 동작한다는 점이 다릅니다.

핵심 개념

  • 플러그인(plugin): 스마트폰 앱처럼 헤르메스에 기능을 추가로 설치하는 것. 설치 후 "켜기(enable)"까지 해야 작동합니다.
  • 스냅숏(snapshot): 지우기 직전에 찍어 두는 사진. 사진이 있으니 원래대로 돌릴 수 있습니다.
  • 효과(effect): 봇의 명령 때문에 실제로 바뀐 파일. undo-effects 는 이 목록을 시간순으로 보여 줍니다.
  • 복원(restore): 사진을 보고 원래 자리에 다시 놓는 것. 미리보기(--dry-run)로 먼저 확인할 수 있습니다.
  • not covered: "이건 제가 사진을 못 찍었어요"라는 정직한 표시. 이 표시가 붙은 것은 되살릴 수 없습니다.

실습: 따라 하기

실습은 반드시 연습용 폴더에서만 합니다. 크론잡이 쓰는 진짜 파일로 연습하지 않습니다.

  • 1인 크리에이터: 크론잡 규칙에 "기록 파일이나 디자인.md 를 바꾸기 전에는 바꿀 내용을 텔레그램으로 먼저 보여 줘"를 추가하고, undo-effects 를 마지막 안전망으로 둡니다.
  • 소상공인: 봇이 관리하는 가격표, 재고 메모 파일이 있다면 "매주 /undo-effects list 를 보고 이상한 삭제가 없었는지 알려 줘" 크론잡을 만듭니다.
  • 강사: 수강생 과제 파일을 봇이 정리하게 할 때, 정리 전후로 list 를 캡처해 두면 실수 추적이 쉽습니다.
  • 직장인: 보고서 초안을 봇이 계속 고쳐 쓰는 작업이라면, 마음에 들던 이전 버전으로 restore 해서 비교합니다.
  • 튠업과 묶기: 일요일 튠업 프롬프트에 "/undo-effects doctor 결과"를 한 줄 추가합니다.

수강생 미션

기본 미션

  • 2~5단계를 따라 연습 파일을 지우고 되살립니다.
  • 제출물: /undo-effects list 화면과 복원 후 memo.txt 내용 화면 캡처 각 1장.

도전 미션

  • 연습 파일을 지우는 대신 sed -i 로 글자를 바꾸게 한 뒤 되돌려 봅니다.
  • git clean 같은 "not covered" 명령이 목록에 어떻게 표시되는지 연습 폴더에서 확인합니다. (연습 폴더 밖에서는 절대 하지 않기)
  • 제출물: not covered 표시 화면 캡처 + "왜 이것은 되살릴 수 없는지" 한 줄 설명.

체크리스트

  • 헤르메스 버전이 0.22.7 이상인지 확인했다
  • 설치 명령을 미리보기로 보고 통과했다
  • hermes plugins list 에서 undo-effects 가 enabled 로 보인다
  • 연습 폴더에서만 삭제 실습을 했다
  • restore 전에 --dry-run 으로 미리보기를 했다
  • 복원 후 파일 내용이 원래대로인 것을 확인했다
  • 이 플러그인이 되돌리지 못하는 것(버퍼 예약, 보낸 메시지 등)을 이해했다

주의할 점과 한계

  • 파일만 되돌립니다. 버퍼에 걸린 예약, 텔레그램으로 보낸 메시지, MCP 로 한 작업은 되돌리지 못합니다(설명서에 v1 범위 밖이라고 명시). 발행 사고는 5차시 승인 규칙으로 막아야 합니다.
  • 지원 안 되는 명령이 있습니다. git clean, git reset --hard, xargs rm, find -exec, 파이썬 코드로 직접 쓰는 경우 등은 "not covered"로 표시만 되고 사본이 없습니다.
  • .env 같은 비밀 파일은 일부러 저장하지 않습니다. 키가 든 파일이 지워지면 이 플러그인으로는 못 살립니다. API 키는 구글 시트 등 따로 보관하라는 4차시 원칙을 지킵니다.
  • 사본은 암호화되지 않습니다. 서버의 HERMES_HOME/plugin-data/undo-effects/ 폴더에 그대로 저장되고 기본 14일 보관됩니다. 평범한 이름의 파일에 비밀을 적어 두면 그것도 복사됩니다.
  • 봇이 저장소 폴더 자체를 지우면 막을 수 없습니다. 설명서가 직접 밝힌 한계입니다. 깃허브 백업과 함께 쓰는 이중 안전망으로 생각합니다.
  • 원격 실행 환경에서는 작동하지 않습니다. 터미널이 원격 샌드박스로 설정돼 있으면 동작하지 않고 doctor 가 경고합니다. 우리처럼 서버에서 직접 도는 기본 설정은 해당됩니다.
  • 커뮤니티 플러그인입니다. 공식 카탈로그 심사는 거쳤지만 Nous Research 가 만든 것은 아닙니다. 설명서에는 헤르메스 0.22.7 에서만 시험했다고 적혀 있습니다.
  • 텔레그램에서 /undo-effects 슬래시 명령이 동작하는지는 직접 시험하지 못했습니다. 공식 문서상 플러그인 슬래시 명령은 게이트웨이 세션에도 등록되지만, 안 되면 5단계의 서버 명령 방식으로 대신합니다.
  • 원문의 설치 명령(hermes plugins install undo-effects --enable)은 공식 문서의 --enable 옵션 설명과 일치합니다. 저장소 설명서는 install 과 enable 을 두 줄로 나눠 적었는데 결과는 같습니다.

강사 노트

시간 내용
0~3분 "깃허브 백업은 전체 되감기, undo-effects 는 방금 지운 것 되살리기" 비교
3~8분 1~2단계 버전 확인과 설치 (강사 봇으로 먼저 시연)

시연 팁:

  • 강사 서버에는 수업 전에 미리 설치하고 게이트웨이 재시작까지 끝내 둡니다. 현장 설치는 시간이 밀릴 수 있습니다.
  • 삭제 장면에서 "앗, 지워졌다" 하고 잠깐 멈추면 복원의 감동이 커집니다.
  • list 화면의 not covered 줄을 일부러 하나 만들어 두면 한계를 설명하기 좋습니다.

예상 질문:

  • Q. 크론잡이 잘못 올린 쓰레드 글도 되돌릴 수 있나요? A. 아니요. 이 플러그인은 서버 안의 파일만 되살립니다. 발행은 미리보기와 "통과" 규칙으로 막습니다.
  • Q. 보관된 사본 때문에 서버 용량이 차지 않나요? A. 기본 14일이 지나면 정리되고, 파일 하나 50MB, 한 번에 200MB 까지만 저장합니다. /undo-effects prune 으로 직접 정리할 수도 있습니다.
  • Q. 체크포인트(/rollback)와 뭐가 달라요? A. 체크포인트는 헤르메스 내장 기능이지만 기본으로 꺼져 있고 git 방식으로 저장합니다. undo-effects 는 켜기만 하면 일반 폴더에서도 파일 단위로 되살립니다. 둘을 같이 써도 됩니다.

AI 직원 채용하기, 프로필과 크론으로 주간 리서치 담당 만들기

책상, 직무기술서, 교육, 수첩, 근무표, 결재까지 8단계로 직원 한 명 뽑기

A 확장졸업 후 과제, 다음 크론잡30분중급
원본 사례: @BkashJosi · 2026-11-03

한 줄 요약

헤르메스에 "직원"을 한 명씩 채용한다. 직원마다 별도 프로필(책상)을 주고, 한 가지 일만 맡기고, 일시정지 상태의 크론잡(근무표)으로 시작해 확인한 뒤 켠다.

원본 사례

헤르메스 팁을 꾸준히 올리는 @BkashJosi(Hermes Super-Intel)는 2026년 11월 3일 "이번 주에 직원 2명부터 뽑아 보라"는 글을 올렸다.

  • 리서치 직원: 매주 월요일, 내 주제의 새 arXiv 논문을 찾아 링크가 달린 5줄로 보내 준다. 스킬은 arxiv, grounded-citations.
  • 코딩 직원: 평일 오전 9시, 열려 있는 풀 리퀘스트와 실패한 검사를 보고 무엇부터 고칠지 초안으로 정리한다. 스킬은 github.

직원마다 자기 프로필, SOUL.md, 메모리, 그리고 일시정지된 근무표를 갖는다. 두 직원 모두 같은 8단계다. (@BkashJosi, 번역)

본인 답글에는 리서치 직원을 만드는 명령 두 줄을 공개했다.

서버 터미널
hermes profile create researcher --description "Weekly sourced paper digest"
hermes -p researcher cron create "0 9 * * 1" "Find this week's new arXiv papers on <your topic>. 5 bullets, each with its link. Draft only." --skill arxiv --skill grounded-citations

함께 링크한 X 아티클 "8 steps to hire Hermes Agent employee"에서는 직원 하나가 여섯 가지로 이뤄진다고 설명한다.

직원의 구성 헤르메스 기능
책상 프로필
직무기술서 SOUL.md
교육 스킬
업무 수첩 메모리 (MEMORY.md, USER.md)
근무표 크론잡
관리자 결재 승인(approvals) 설정

아티클의 핵심 조언은 세 가지다. 직무를 한 문장으로 쓰고, 직원마다 책상(프로필)을 따로 주고, 새 직원은 수동 결재(manual)로 시작하라는 것이다. "그리고 또"가 필요하면 그건 두 번째 직원이라고 한다.

왜 헤르메스반에 중요한가

우리는 3차시에 밤 11시 크론잡을 걸었고, 5차시에 "미리보기 → 통과 → 버퍼 예약" 규칙을 붙였다. 지금은 봇 하나가 모든 일을 한다.

  • 다음 크론잡을 어디에 둘까: 크론잡이 늘어나면 한 봇의 메모리와 규칙이 섞인다. 블로그 담당 규칙이 뉴스 요약에 새어 나가는 식이다. 직원(프로필)을 나누면 섞이지 않는다.
  • 일시정지 상태로 시작: 5차시의 "답 없으면 발행 안 함" 규칙과 같은 정신이다. 처음부터 켜지 않고, 한 번 읽어 보고 켠다.
  • 초안만: 원문 직원도 "Draft only(초안만)"가 기본이다. 우리 수업의 승인 습관과 같다.
  • 졸업 후 혼자 확장하는 틀: 8단계를 한 번 익히면 아침 브리핑, 메일 정리 같은 직원을 같은 방법으로 계속 뽑을 수 있다.

구조 한눈에 보기

  1. 1직무 한 문장매주 월요일, 내 분야 뉴스 5줄을 링크와 함께 초안으로
  2. 2책상(프로필)hermes profile create 로 별도 공간 만들기
  3. 3직무기술서(SOUL.md)한 가지 일과 하지 말아야 할 일 적기
  4. 4교육(스킬)필요한 스킬만 붙이기
  5. 5근무표(크론)일시정지로 만들고, 읽어 보고, 켜기
  6. 6결재와 평가결과를 일주일 보고 계속 둘지 결정

핵심 개념

  • 프로필: 직원의 책상. 설정, 메모리, 스킬, 크론잡이 따로 보관된다. 프로필 이름이 곧 명령어가 된다 (예: researcher chat).
  • SOUL.md: 직원의 직무기술서. 시스템 프롬프트 맨 앞에 들어가 "나는 누구이고 무엇을 하는가"를 정한다.
  • 스킬: 직원 교육 매뉴얼. 필요한 것만 붙여야 딴짓을 덜 한다.
  • 크론 표현식: 근무 시간표. 0 9 * * 1은 "매주 월요일 9시 0분", 0 9 * * 1-5는 "평일 9시".
  • 일시정지(paused) 생성: 스위치를 끈 채로 설치하기. 내용을 확인한 뒤 resume으로 켠다.

실습: 따라 하기

수업용으로 원문의 arXiv 논문 예시를 "내 분야 뉴스 주간 브리핑"으로 바꿨다. 수강생 서버에서 바로 해 볼 수 있는 가장 쉬운 길(기존 텔레그램 봇에서 만들기)과 원문 방식(별도 프로필)을 차례로 해 본다.

1단계: 직무를 한 문장으로 쓰기

아티클의 빈칸 채우기 공식이다.

매 [언제], [한 가지 일]을 해서 [하나의 결과물]을 내가 [승인/읽기/사용]하게 준다.

예시: "매주 월요일 오전 9시, 내 분야(예: 소상공인 마케팅) 이번 주 뉴스 5개를 찾아서, 각 줄에 출처 링크를 단 초안을 내가 읽게 준다."

10초 안에 결과가 좋은지 나쁜지 판단할 수 있으면 잘 쓴 문장이다.

2단계: 기존 봇으로 먼저 시험 근무 시키기

새 프로필을 만들기 전에, 지금 텔레그램 봇에서 한 번만 실행해 결과 품질을 본다.

텔레그램 · 내 봇에게
지금 한 번만 해 줘. 크론잡은 아직 만들지 마.
소상공인 마케팅 분야에서 이번 주 나온 국내 뉴스 5개를 찾아서
한 줄 요약 + 출처 링크로 정리해 줘.
확인 못 한 내용은 추측하지 말고 "미확인"이라고 적어.

결과가 마음에 들 때까지 문장을 다듬는다. 이 문장이 그대로 크론잡 지시문이 된다.

3단계: 일시정지 상태로 근무표 만들기 (기존 봇)

텔레그램에서 만든 크론잡은 결과가 같은 대화방으로 온다.

텔레그램 · 내 봇에게
2단계 지시문으로 크론잡을 하나 만들어 줘.
이름: 주간 뉴스 브리핑
시간: 매주 월요일 오전 9시 (한국 시간)
스킬: 웹 검색과 출처 표기에 필요한 것만
처음에는 일시정지 상태로 만들고, 만든 내용(시간, 지시문, 스킬)을 보여 줘.
내가 "켜"라고 하면 그때 켜 줘.

봇이 보여 준 내용을 읽고 "켜"라고 답한다. 바로 시험하려면 "지금 한 번 실행해 줘"라고 한다.

4단계: 별도 직원(프로필)으로 독립시키기

원문 방식이다. 라이트하우스 서버 까만 창에서 하거나, 봇에게 명령 실행을 맡긴다.

서버 터미널
hermes profile create newsdesk --description "매주 내 분야 뉴스 5개를 출처 링크와 함께 요약하는 담당"
hermes profile list

직무기술서를 쓴다. 봇에게 맡겨도 된다.

텔레그램 · 내 봇에게
newsdesk 프로필의 SOUL.md를 아래 내용으로 바꿔 줘. 바꾸기 전에 전체 내용을 먼저 보여 주고 내 승인을 받아.

[뉴스데스크]
너는 뉴스데스크 직원이다.
[한 가지 일]
매주 내 분야 뉴스 5개를 한 줄 요약과 출처 링크로 정리한다.
[규칙]
- 초안만 만든다. 어디에도 게시하거나 보내지 않는다.
- 모든 줄에 공식 출처 링크를 단다.
- 확인 못 한 것은 "미확인"이라고 쓴다.
- 모든 답을 "뉴스데스크:"로 시작한다.

"뉴스데스크:"로 시작하는지 보면 직무기술서가 적용됐는지 바로 알 수 있다.

5단계: 직원의 근무표 만들기

원문 명령 구조를 따른 예시다. -p newsdesk는 "이 명령을 newsdesk 직원에게"라는 뜻이다.

서버 터미널
hermes -p newsdesk cron create "0 9 * * 1" "이번 주 소상공인 마케팅 국내 뉴스 5개를 한 줄 요약과 출처 링크로 정리해. 초안만." --name "주간 뉴스 브리핑" --skill grounded-citations --paused --paused-reason "첫 실행 전 확인"
hermes -p newsdesk cron list
hermes -p newsdesk cron resume <작업ID>

6단계: 일주일 평가

서버 터미널
hermes -p newsdesk cron runs

매주 한 줄씩 기록한다: 날짜, 실행됐는지, 결과, 내가 채택했는지. 쓸모없으면 해고한다.

서버 터미널
hermes -p newsdesk cron remove <작업ID>
hermes profile delete newsdesk -y

삭제 전에 SOUL.md는 따로 복사해 둔다.

응용 아이디어

  • 소상공인: "매일 오전 8시, 우리 가게 네이버 리뷰 새 글을 모아 답글 초안 3개를 준다."
  • 1인 크리에이터: "매주 금요일, 내 분야 유튜브 인기 주제 5개를 쇼츠 아이디어 초안으로 준다."
  • 강사: "매주 일요일 밤, 다음 주 수업에 쓸 최신 사례 3개를 출처와 함께 준다."
  • 직장인: "평일 오전 7시, 오늘 일정과 중요한 메일을 5줄로 요약해 준다." (원문 아티클의 Morning Brief)
  • 블로거: "매주 월요일, 지난주 블로그 글 중 쓰레드로 다시 쓸 만한 글 1개를 골라 준다."

수강생 미션

기본 미션

1~3단계를 따라 기존 텔레그램 봇에 "주간 브리핑" 크론잡을 일시정지 상태로 만들고, 내용을 확인한 뒤 켠다. "지금 한 번 실행"으로 결과를 받아 본다.

제출물: 직무 한 문장, 크론잡 내용 캡처, 첫 실행 결과 캡처.

도전 미션

4~6단계를 따라 별도 직원(프로필)을 하나 뽑고, SOUL.md와 일시정지 근무표까지 만든다. 일주일 동안 근무 기록표를 쓴다.

제출물: hermes profile list 캡처, "뉴스데스크:"로 시작하는 답변 캡처, 일주일 근무 기록표(날짜, 실행 여부, 채택 여부).

체크리스트

  • 직무를 "매 [언제], [한 가지 일], [하나의 결과물]" 한 문장으로 썼다
  • 크론잡을 만들기 전에 한 번 수동 실행으로 품질을 확인했다
  • 크론잡을 일시정지 상태로 만들고 내용을 읽은 뒤 켰다
  • 지시문에 "초안만", "출처 링크", "미확인 표기"가 들어 있다
  • (도전) 프로필 SOUL.md가 적용된 것을 응답 머리말로 확인했다
  • 일주일 뒤 계속 둘지 해고할지 결정했다

주의할 점과 한계

  • 게이트웨이가 꺼지면 근무도 멈춘다: 크론잡은 게이트웨이가 실행한다. 봇이 조용하면 hermes gateway restart부터 한다.
  • 새 프로필은 빈 책상: 기본 생성은 메인 봇의 메모리와 성격을 가져가지 않는다. 아티클에 따르면 터미널에서 만든 프로필에는 OAuth 로그인도 복사되지 않아 hermes -p <이름> auth add로 따로 연결해야 할 수 있다. 우리 수업처럼 ChatGPT 구독(OAuth)을 쓰면 새 프로필에서 다시 인증이 필요할 수 있다.
  • 새 직원의 결과를 텔레그램으로 받으려면: 공식 문서상 텔레그램 봇 하나는 한 프로필에만 속한다. 별도 프로필의 결과를 텔레그램으로 받으려면 그 프로필에 메시징 설정이 따로 필요하다. 어렵다면 기본 미션처럼 기존 봇에서 크론잡을 만드는 것이 가장 쉽다. 터미널에서 만든 크론잡의 기본 전달 위치는 서버 안 파일(local)이다.
  • --deliver 플래그: 원문 아티클은 --deliver local 같은 플래그를 쓴다. 공식 문서에서 전달 대상 값(origin, local, telegram)은 확인했지만, 이 플래그 이름 자체는 원문 작성자 제공이며 공식 문서에서 직접 확인하지 못했다.
  • "초안만"은 잠금장치가 아니다: SOUL.md 규칙은 지침일 뿐이다. 위험한 명령을 막는 것은 승인(approvals) 설정이고, 크론 실행 중 위험 명령은 기본값(cron_mode: deny)으로 차단된다.
  • arXiv 예시는 영어권 논문용: 원문 arxiv 스킬은 논문 검색 전용이다. 국내 뉴스용으로는 웹 검색과 출처 표기 스킬을 쓴다.
  • 아티클의 전제 버전: 원문 아티클은 Hermes Agent v0.22 이상을 전제로 한다. 수강생 서버 버전이 낮으면 명령이 다를 수 있다.

한 줄 요약

헤르메스로 사업을 운영하던 비개발자가, 예전에 한 번 연결해 둔 트윗 삭제 앱 때문에 X 계정의 글을 모두 잃었다. 범인은 에이전트가 아니라 "반복 작업인 줄 몰랐던" 외부 앱이었고, 교훈은 연결한 출입증과 예약 작업을 주기적으로 점검하고 백업하라는 것이다.

원본 사례

GreyMatter(@greymatter_hq)는 아랍어와 영어를 함께 쓰는 지역에 사는 사업 운영자이자 컨설턴트다(지역은 글에 나온 언어로 추정). 산업공학을 전공하고 PMP, MBA를 가졌으며, 은행에서 재무 모델을 만들었고 강의 경험도 있다. 연매출 800만 달러 이상, 여러 나라에서 운영하는 다사업부 회사의 운영을 돕고 있고, 별도로 컨설팅 회사 GreyMatter를 운영한다고 소개한다(규모는 작성자 주장). 그리고 스스로 "나는 개발자가 아니다"라고 강조한다.

그는 X에 "How Hermes Agent changed my business and my life(헤르메스가 내 사업과 삶을 바꾼 방법)"라는 긴 글을 썼다. 알림 몇 개로 시작한 헤르메스가 지금은 회사 전략과 숫자, 고객사 사전 감사, 전시 부스 3D 설계, 친구들의 식당 예약, 병원 기록 정리까지 돕는다는 내용이다.

그런데 2026년 11월 19일, 그는 이 글을 다시 올리며 이렇게 썼다.

"한 번 연결했던 트윗 삭제 앱이 오늘 내 계정을 지워 버렸다. 이 글도 포함해서." (@greymatter_hq, 번역)

답글에서 경위가 나왔다. 옛날 트윗을 지우려고 한 번 쓴 앱이었는데, 그것이 반복 작업으로 설정되어 있다는 것을 몰랐다. 그리고 분명히 했다. "에이전트가 아니었다. 서드파티 소프트웨어였다."

다른 사용자(@dynbuzzdigital)가 남긴 답글도 교훈적이다. 자기 에이전트는 초안은 얼마든지 만들 수 있지만, 이미 게시된 것을 고치거나 지우는 일은 자기가 정한 정확한 문구 없이는 못 하게 해 두었다며 "나쁜 초안은 버리면 되지만, 지워진 계정은 되돌릴 수 없다"고 말했다.

흥미로운 점은 원래 글 안에 이미 정답이 적혀 있었다는 것이다. 작성자는 "처음 시작한다면" 부분에서 이렇게 권한다.

  • 보내기, 게시, 지출, 삭제, 계정 변경 전에는 반드시 물어보게 한다.
  • 일에 필요한 접근 권한만 준다.
  • 예약 작업에 의존하기 전에 결과가 어디로 오는지, 실패하면 어떻게 알 수 있는지, 어떻게 끄는지 확인한다.
  • 백업을 유지한다.
  • 비밀번호나 키는 절대 채팅에 붙여 넣지 않는다.

그는 헤르메스에는 이 원칙을 지켰지만, 오래전에 연결한 다른 앱에는 같은 기준을 적용하지 못했다.

왜 헤르메스반에 중요한가

우리 수업의 흐름이 그대로 겹친다.

  • 5차시에 버퍼 API 키를 만들어 봇에게 줬다. 이 키는 유효 기간이 1년이다. 수업이 끝나도 키는 살아 있다.
  • 3차시부터 밤 11시 크론잡이 매일 돌고 있다. 크론잡은 "반복 작업"이다. 작성자를 당한 바로 그 종류다.
  • 5차시에 "통과"라고 답해야만 예약되고, 다음 날 8시까지 답이 없으면 발행하지 않는 규칙을 넣었다. 이것이 @dynbuzzdigital이 말한 "정확한 문구 없이는 못 한다" 규칙과 같은 원리다.

즉, 우리 봇은 이미 좋은 습관을 갖고 있다. 이번 사례는 그 습관을 봇 밖, 내가 연결한 모든 앱과 예약 작업으로 넓히라는 이야기다.

구조 한눈에 보기

  1. 1옛 트윗 정리하려고 앱 연결쓰기, 삭제 권한을 한 번 허락
  2. 2일은 끝났다고 생각하고 잊음연결과 권한은 그대로 남음
  3. 3앱이 반복 작업으로 계속 실행반복 설정인 줄 몰랐음
  4. 4어느 날 새 글까지 모두 삭제아끼던 긴 글도 함께 사라짐
  5. 5교훈연결 점검, 예약 작업 점검, 삭제는 승인, 백업

핵심 개념

  • 서드파티 앱 연결(OAuth): 건물 출입증을 외부 업체에 발급하는 것. 업체가 일을 끝내도 내가 회수하지 않으면 출입증은 계속 유효하다.
  • 반복 작업(크론잡): 매일 같은 시간에 울리는 알람. 한 번 맞춰 두면 끌 때까지 울린다.
  • 되돌릴 수 있는 일과 없는 일: 초안 만들기는 연필, 게시와 삭제는 볼펜. 볼펜으로 쓰는 일은 반드시 내 확인을 거친다.
  • 백업: 집 열쇠 복사본을 믿을 만한 곳에 하나 더 두는 것. 헤르메스는 hermes backup으로 에이전트 전체를 zip 하나로 저장한다.
  • 승인 기본값 거부: 헤르메스는 승인 요청에 답이 없으면 실행하지 않는다(공식 문서 기준 기본 300초 후 거부). 크론잡은 위험한 명령을 만나면 기본적으로 차단된다(cron_mode: deny).

  • X: 설정 > 보안 및 계정 접근 > 앱 및 세션 > 연결된 앱
  • 구글: 구글 계정 > 보안 > 서드파티 앱 및 서비스(타사 연결)
  • 버퍼: 계정 설정의 API 키, 연결된 앱 화면
  • 인스타그램, 쓰레드: 설정 > 웹사이트 권한 또는 앱 및 웹사이트

5단계: 백업 한 번 만들기

서버 까만 창에서 실행한다.

서버 터미널
hermes backup

공식 문서에 따르면 백업 zip에는 모든 프로필, 기억, 스킬, 대화, 예약 작업, 설정, 그리고 키와 로그인(.env, auth.json)까지 들어간다. 그래서 이 파일은 "출입증 묶음"이다. 공개 저장소나 단톡방에 올리지 말고 개인 저장 공간에만 둔다. 복원은 hermes import <zip 파일>로 한다.

응용 아이디어

  • 소상공인: 배달앱, 스마트스토어에 연결된 리뷰 관리, 자동 답글 앱을 분기마다 한 번 점검하는 "출입증 정리의 날"을 달력에 넣는다.
  • 1인 크리에이터: 유튜브, 인스타에 연결된 예약 도구를 정리하고, 아끼는 글과 영상은 봇에게 매주 일요일 목록과 링크를 백업 문서에 기록하게 한다.
  • 강사: 수업 때 실습으로 만든 API 키는 기수가 끝나면 재발급하거나 폐기한다. 수강생에게도 종강일에 "키 정리"를 과제로 낸다.
  • 직장인: 회사 계정에 붙인 생산성 앱 목록을 만들어, 퇴사나 부서 이동 때 반드시 해제한다.
  • 팀 단위: 봇이 할 수 있는 일을 "연필 작업(초안)"과 "볼펜 작업(게시, 전송, 지출, 삭제)"으로 나눠 표로 붙여 두고, 볼펜 작업은 담당자 승인 문구를 정한다.

수강생 미션

기본 미션

1단계로 X 또는 구글의 연결된 앱 목록을 점검하고, 해제한 앱이 있으면 개수를 적는다. 2단계 크론잡 표를 받아 제출한다. 제출물: 크론잡 표 캡처 1장 + "해제한 앱 N개" 한 줄.

도전 미션

3단계 규칙(삭제 금지, 정확한 승인 문구)을 크론잡에 추가하고, 5단계 백업 zip을 만들어 개인 저장소에 보관한다. 제출물: 수정된 크론잡 전문 캡처 + 백업 파일 이름과 크기만 보이는 캡처(파일 내용은 공유 금지).

체크리스트

  • X, 구글, 버퍼에 연결된 외부 앱 목록을 직접 확인했다
  • 쓰지 않는 앱, 기억나지 않는 앱의 연결을 해제했다
  • 내 봇의 크론잡을 모두 알고, 각각 무엇을 바깥에 쓰는지 안다
  • 게시, 삭제처럼 되돌릴 수 없는 일은 승인 문구 없이 실행되지 않는다
  • 크론잡이 실패하면 알 수 있는 방법과 끄는 방법을 안다
  • hermes backup 파일이 있고, 공개된 곳에 올리지 않았다
  • 수업용으로 만든 키의 유효 기간과 폐기 시점을 정했다

주의할 점과 한계

  • 이 사고의 직접 원인은 헤르메스가 아니라 외부 트윗 삭제 앱이다(작성자 본인 설명). 앱 이름, 준 권한, 계정 복구 여부는 공개되지 않아 확인하지 못했다.
  • 그렇다고 에이전트는 안전하다는 뜻이 아니다. 삭제, 게시 권한을 가진 크론잡은 구조적으로 똑같은 위험을 가진다.
  • 백업 zip에는 키와 로그인이 들어 있으므로, 백업 자체가 새로운 유출 경로가 될 수 있다.
  • 헤르메스의 승인 화면에서 "always(항상 허용)"를 고르면 그 명령 유형이 영구 허용 목록에 저장된다. 편하다고 누르지 않는다.
  • 작성자 글 속 사업 규모, 월 400달러 비용, 모델별 테스트 점수, 모델 이름은 작성자 주장이며 검증하지 않았다.
  • X, 구글의 메뉴 경로는 개편에 따라 바뀔 수 있다.
